# Custom dictionary on device

The Speechmatics on-device SDK supports [custom dictionary](/speech-to-text/features/custom-dictionary): words and phrases you add to a job so that the SDK recognizes them, such as names, product terms and jargon.

## Add a custom dictionary to a job

Your application passes the custom dictionary in the JSON job config given to `sm_transcribe`, as `additional_vocab` inside `transcription_config`:

```json title="job_config.json"
{
  "transcription_config": {
    "additional_vocab": [
      { "content": "Speechmatics" },
      { "content": "gnocchi", "sounds_like": ["nyohki", "nokey"] }
    ]
  }
}
```

Each entry has a `content` value, the word or phrase as it should appear in the transcript, and optionally `sounds_like`, a list of pronunciations written as they sound. When an entry has `sounds_like`, the SDK pronounces it only from those values, not from the spelling in `content`. The [custom dictionary](/speech-to-text/features/custom-dictionary) page describes both fields and the limits on what you can add.

Pass the job config as a string to `sm_transcribe`:

```cpp
// Transcribe with a custom dictionary
const std::string job_config =
    R"({"transcription_config":{"additional_vocab":[{"content":"Speechmatics"}]}})";
SMTranscriptionResult result = sm_transcribe(engine, audio.c_str(), audio.size(),
                                             job_config.c_str(), job_config.size());
```

With the reference app, put the job config in a file and pass it with `-j job_config.json`.

## How custom dictionary differs on device

On-device custom dictionary follows SaaS on Cloud, with these differences:

- **Unpronounceable `sounds_like` entries are dropped.** If none of an entry's `sounds_like` values can be pronounced, the SDK leaves the entry out and logs a warning naming it. SaaS on Cloud pronounces such an entry from its `content` instead.
- **`sounds_like` must be a non-empty list of strings.** Otherwise `sm_transcribe` returns `SMTranscriptionInvalidJobConfig`.
- **Control characters are rejected.** A line break or other control character in `content` or `sounds_like` returns `SMTranscriptionInvalidJobConfig`. A tab counts as a space.
- **Spaces split words.** An ASCII space in `content` splits it into separate words in the transcript. Any other space character, such as a no-break space, keeps it one word.

## How the SDK compiles a custom dictionary

The SDK compiles each job's custom dictionary before transcribing, using `cd-compiler`, a helper program that ships in the SDK's `bin/` directory. Compiling adds time to the start of the job, so the SDK can [cache compiled dictionaries](#cache-compiled-custom-dictionaries).

The SDK looks for `cd-compiler` beside its own library, then in the `bin/` directory next to the library's directory. If `cd-compiler` isn't there, a job with `additional_vocab` fails. Jobs without a custom dictionary are unaffected.

If you install the SDK's files in a different layout, set the `SM_CD_COMPILER_PATH` environment variable to the path of `cd-compiler`. On Windows, copy `cd-compiler` and its files with the SDK DLLs. With CMake, `speechmatics_esl_copy_runtime` does this for you.

## Cache compiled custom dictionaries

To reuse compiled dictionaries, call `sm_set_custom_dictionary_cache` with a directory, before creating any engine:

```cpp
// Keep compiled custom dictionaries in a directory only this application uses
const std::string cache_dir = "/path/to/my_app/cd-cache";
sm_set_custom_dictionary_cache(cache_dir.c_str(), cache_dir.size());
```

A later job with the same `additional_vocab` then uses the compiled dictionary from the cache instead of compiling it again, which is much faster.

The cache is off by default, and there is no default directory: unless your application calls `sm_set_custom_dictionary_cache`, the SDK caches nothing and writes nothing. When choosing the directory:

- **Use a directory only your application uses,** and one the process can write to. The SDK creates it if it doesn't exist.
- **Clean it up yourself.** The SDK doesn't remove the directory when your application is uninstalled.
- **Share it freely.** Any number of engines, threads and processes can use the same directory.

The cache holds at most 256 MiB and 64 dictionaries. When it's full, the SDK removes the least recently used dictionaries first. Dictionaries compiled by one SDK version are not used by another.

A cache that can't be used, for example because the directory isn't writable or the disk is full, never fails a job. The SDK compiles the dictionary without the cache and logs a message.

To turn the cache off again, call `sm_set_custom_dictionary_cache(nullptr, 0)`. The setting applies to engines created after the call.

With the reference app, set the cache directory with `--custom-dictionary-cache-dir <dir>`.

## Set the custom dictionary compile timeout

`sm_set_custom_dictionary_timeout_secs` sets how long `cd-compiler` can run for one job before the SDK stops it and the job's custom dictionary fails. The default is 300 seconds:

```cpp
// Allow up to 10 minutes to compile a very large custom dictionary
sm_set_custom_dictionary_timeout_secs(600);
```

The timeout only stops a compile that has hung, as a normal compile takes far less than the default. Raise it only for a very large word list on a slow device. A value of 0, a negative value or a non-finite value restores the default. The setting applies to every engine created after the call, and is safe to call at any time.

## Custom dictionary engine options reference

The SDK provides these process-wide settings for custom dictionary:

| Setting | Default | Description |
|---|---|---|
| `sm_set_custom_dictionary_cache(dir, dir_len)` | Off | Directory to cache compiled custom dictionaries in. `nullptr` or a length of `0` turns the cache off. |
| `sm_set_custom_dictionary_timeout_secs(secs)` | 300 | Seconds `cd-compiler` can run for one job. |
| `SM_CD_COMPILER_PATH` environment variable | Unset | Path to `cd-compiler`, when it isn't in the SDK's own layout. |
